This document is intended to help the user of the RISC-V Development Platform. It describes the correct
usage and configuration options of the toolchain. The prerequisites to understand this document is that you
are familiar with the C language and RISC-V.
This document describes the tools of the RISC-V Development Platform and how they can be used to create
an executable or library from one or more C, C++, or assembly source files. This document also lists some of
the supported options of the tools, both generic options as well as RISC-V-specific ones.

1.1. Conventions
The following typographic conventions are used in this book:
Typography Description
command A command-line interface command, or C, C++, or
assembler statement.
[foo] This string is meant to be substituted by either foo or
an empty string, depending on the user’s intention.
<parameter> This string is meant to be substituted by a
reasonable value, typically described under its usage
in this book.
{foo|bar|baz} This string is meant to be substituted by either foo,
bar, or baz.
These conventions have been adapted from the IEEE 1003 POSIX standard and manual files for the GNU
software tools.
Windows users should note that .exe suffixes are not shown in example command-line invocations of the
programs presented.

1.2. Toolchain components
The HighTec RISC-V Development Platform is a complete tools suite to develop C/C++-based application
software for supported RISC-V devices. The HighTec RISC-V Development Platform utilizes the cutting
edge open source LLVM infrastructure for highly-optimized machine code and high reliability. The RISC-V
Development Platform consists of the following tools:
Compiler driver
The C/C++ compiler driver clang is a complete control program for a large part of the toolchain. It can
orchestrate the entire build of an executable with a single command-line invocation. This invocation is
described in Compiler driver invocation. It can also be used to invoke just one of the following tools.
Preprocessor
The preprocessor prepares the C, C++ or assembly source code for the compiler. In this first state of
the compiling process, the preprocessor directives like #include or #define are interpreted. The
preprocessor merges files, replaces macros, and removes comments from the source code. It can be
generally invoked as clang -E.
Compiler
The C/C++ compiler converts the mostly target-independent high-level language source code to target
assembly or binary machine code. It can be generally invoked as clang -cc1.
Assembler
The assembler generates an object file from assembly. An object file consists of machine code, that will
be executed by the target machine, and data used by the program. However, addresses of code and
data outside of each compilation unit (corresponding to each source file) aren’t yet assigned in the
object file and left "blank" for the linker to fill in. The assembler can be generally invoked as clang
-Xassembler.
Linker
The linker generates an executable by combining the sections of the input object files with objects from
libraries. The locations of code and data sections in memory is configured by a linker script file. The
linker can be invoked through clang with object file inputs, or through the dedicated ld.lld program.
Binutils
The binutils are a collection of programs to manipulate and inspect the files generated by the compiler
tools. These programs are not invoked while executing the compiler driver program but must be
started separately. Disassembling machine code, copying output files from one file format to another or
combining objects into archives are just a few of the tasks that can be done using binutils. The
provided binutils programs have an llvm- prefix.

Chapter 2. Compiler driver
The C/C++ compiler driver clang is a complete control program for a large part of the toolchain. It can
orchestrate the entire build of an executable with a single command-line invocation.
2.1. Invocation of clang
Generic command to start the control program for compiling source code for RISC-V-based microcontrollers:
clang [--target=riscv32-unknown-elf] [<options>] <input file> [<more input files>]
A subset of options available in some components of the toolchain is accessible through clang as a compiler
driver. It accepts these options and passes them to the appropriate component. This chapter explains the
options accepted by clang. If an option is simply passed by clang to the relevant toolchain component, the
description of the option will mention which tool is being targeted by it. Most notably, options specific to
compilation are summarized in Compiler options . Additional information about generic command-line
options is available in the clang and documentation in the community Clang 21.1.0 command line argument
reference. This is equivalent to the output of clang --help.
clang invokes the programs of the toolchain with default argument values. These settings contain default
include paths for libraries and header files. You can find a complete list of the default options for each
program of the toolchain in the section ”Default options” in its chapter. These can be overridden by the user.

There are certain compiler options, which shall be passed to the driver when linking, if they were used

Chapter 3. Preprocessor
The preprocessor prepares the C, C++ or assembly source code for the compiler. In this first state of the
compiling process, the preprocessor directives like #include or #define are interpreted. The preprocessor
merges files, replaces macros, and removes comments from the source code.
The preprocessor is the first program started by clang in the typical compilation process. This first build
step is target-independent since the preprocessor only changes a source file’s text content.
3.1. Preprocessor invocation
The clang preprocessor does not exist as a standalone application. It is automatically invoked by the clang
compiler driver to emit an executable file.
To run only the preprocessing step, combine Invocation of clang with compiler driver option -E.
clang [--target=riscv32-unknown-elf] -E [<preprocessor options>] <input file> [<more input
files>]
The output is preprocessed source code, which clang sends to the standard output, unless -o <file> is set.

Chapter 4. Compiler
The clang compiler is a C/C++ language family frontend for LLVM. It builds on the LLVM optimizer and code
generator, allowing it to provide high-quality optimization and code generation across targets.
clang is designed to act as a replacement for the GNU Compiler Collection (GCC), supporting most of its
compilation flags and unofficial language extensions.
The compiler consists of three parts: the frontend, the middle-end, and the backend. The frontend reads the
input source code, analyzes the objects in it and writes their relationship into a tree structure, the abstract
syntax tree. The frontend then transforms this tree structure into an intermediate representation, called the
LLVM IR. The middle-end runs optimization passes based on analyses of the code. These parts of the
compiler are not very machine-specific, and differ in minor ways across targets. Finally, the compiler
backend transforms the LLVM IR to target-specific machine code and outputs it as assembly sources or
assembled object files. LLVM bitcode is the serialized binary format of LLVM IR.
4.1. Compiler invocation
4.1.1. Generate executable file
The clang compiler does not exist as a standalone application. It is automatically invoked by the clang
compiler driver to emit an executable file.
4.1.2. Generate assembly file(s)
To run only the preprocessing and compilation steps, combine Invocation of clang  with compiler driver
option -S.
clang [--target=riscv32-unknown-elf] -S [<options>] <input file> [<more input files>]
The output is one assembly file per input source file.
4.1.3. Generate object file(s)
To compile and assemble the source files without linking, combine Invocation of clang  with compiler driver
option -c.
clang [--target=riscv32-unknown-elf] -c [<options>] <input file> [<more input files>]
The output is an object file for each input file.
4.2. Compiler options
The compiler can be controlled with certain command line options. Most of these options add or remove
specific optimizations done by the compiler or enable/disable specific features. Generally, options which can

Chapter 5. Assembler
The assembler is a tool that converts assembly code to binary machine code.
5.1. Assembler invocation
The clang integrated assembler does not exist as a standalone application. It is automatically invoked by
the clang compiler driver  to emit an executable file. Just like the gcc compiler driver, you can directly use
clang to assemble assembly into object files or binaries like clang <file>.S. The integrated assembler is
compatible with GNU syntax.
To pass an option to the assembler, which is not directly accessible via clang, you should use the
-Xassembler <arg> or -Wa,<args> option. For example:
clang test.s -Xassembler -asm-opt1 -Xassembler -asm-opt2
clang test.s -Wa,-asm-opt1,-asm-opt2
5.2. Assembler implementation
5.2.1. Syntax
This chapter discusses the assembly syntax supported by the integrated assembler.
STATEMENT:
In assembly language, a statement can be a LABEL, INSTRUCTION, DIRECTIVE, or a macro and all
statements end with a newline character(\n). The assembler is not whitespace-sensitive.
LABEL:
A label statement ends with a colon ( :). It represents the current value of the active location counter. Labels
can be used as placeholders inside assembly code.
A label name without a double quote must fulfill the following properties:
• Must start with a period (.), underscore(_), a-z, or A-Z.
• Can also contain numbers, underscore(_) and $ sign.
• Must not contain whitespace characters.
In case the label name contains whitespace characters, it must be surrounded by double quotes.
Code 1. label example
.LB001          // This is a legal label.
.LB 0001        // This is an illegal label.
"func start"    // Label with spaces surrounded by double quotes.
INSTRUCTION:

An instruction ends with an optional semi-colon( ;). Multiple instructions separated with ; can be written on
the same line.
Code 2. instruction example
add a1, a1, a2; jal foo    // Add two registers and jump
jalr a1                      // Jump to the address in the return address register
DIRECTIVE:
All assembler directives have names that begin with a period ( .). The rest of the name is letters, usually in
lower case. A directive ends with an optional semi-colon( ;). Multiple directives separated with ; can be
written on the same line.
COMMENT:
There are multiple ways to add comments into assembly code.
You can insert a single-line comment by starting the comment with // or #.
Code 3. single-line comment example

You can add a multiline comment with using /* */ signs.

5.2.2. Expression
An expression is a collection of symbol references and/or integer constants. The result of the expression
must either be an absolute value or an offset. If an expression is not an absolute value, then the assembler
emits an error message.
An expression can have one of the following forms:
An absolute value, or expression (not involving labels) which evaluates to one. For example:
Code 5. Expression example 1

Chapter 6. Linker
The linker ( ld.lld) takes one or more object or archive files, and combines them into an output file (an
executable or another object file). It relocates code and data from the input files and resolves symbol
references between them.
6.1. Linker invocation
The linker can either be invoked directly by calling ld.lld or through the toolchain driver clang. The
general syntax to invoke ld.lld is as follows:
ld.lld <options> <input-files>
The following example shows how to produce an executable binary called output.elf by linking together
the contents of file1.o and file2.o and the library libfoo.a:
ld.lld -o output.elf file1.o file2.o -lfoo
This is assuming that libfoo.a is in the library search path. You can add it by adding -L<directory-with
-libfoo.a>.
Instead of calling the linker directly, we recommend to use the toolchain driver clang instead. It will
automatically choose appropriate options and libraries based on the given options. Using clang, the
example from above looks as follows:
clang -o output.elf file1.o file2.o -lfoo
Although clang understands and forwards most of the common linker options, some need to be passed
directly to the linker. To pass an option to the linker, you should use the -Xlinker or -Wl option. For
example:
clang test.c -Xlinker -l<libname> -Xlinker -Map
clang test.c -Wl,-l<libname>,-Map

6.3. Sections and relocation
The object and library files used as input to the linker contain sections and relocations. The output files of a
link process also contain sections and resolved relocations.
Roughly, a section is a range of addresses, with no gaps. Input sections are sections from input files that
contain code, data or memory, that the linker must initialize. They might also contain references to external
code or data, which the linker has to resolve during link time. Sections have attributes that mark their
purpose. For example, there may be a read-only (RO) section.
An Output section is a group of input sections that share the same attributes. All input sections within one
output section are placed contiguously in memory. The order of the input sections within an output section
is controlled by the Linker script , which contains directives for the linker how to put the different input
sections together.

ld.lld also assigns run-time addresses to sections and it resolves references to other code or data. This
process is called relocation. Relocation might also involve generating special code constructs to increase the
jump range of branch instructions, in case branch targets are out of range. To let the linker know how
certain relocations should be resolved, the compiler inserts relocation details where relocations are
necessary (e.g. jump targets). This tells the linker if a relocation should for example be resolved as a relative

6.4.9. OVERWRITE_SECTIONS command

{

the definition provided by OVERWRITE_SECTIONS takes precedence. If the output section is not defined in a

directive remains in effect and may be applied after orphan section placement. Since the section definition in
the INSERT command is ignored in this case, it is recommended to use an empty section body (for example,
section : {}) within the INSERT directive.

• Use this definition for the output section .foo.
• Place all input sections named .foo into it.
• Define foo_start andfoo_end symbols.
• Let LLD decide where .foo should be placed in the final output.

6.4.12. REGION_MIRROR Command
The REGION_MIRROR linker script command instructs the linker to treat the memory regions that are
referenced by the command as they were for the same physical memory area, but with different addresses.
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   64
--- PAGE 71 ---
SYNTAX:
REGION_MIRROR(`<RegionNameOrAlias>`, `<RegionNameOrAlias>`, ...)
DESCRIPTION:
The command must be specified at the top level of a linker script, after any memory regions are defined by
the MEMORY command, optionally after some REGION_ALIAS commands, but before any SECTIONS command.
<RegionNameOrAlias>
can be any memory region name or memory region alias that already exists (i.e. it has been declared

mirrored allocation, i.e. advancing the location counter for one region has to advance the counters of all its
mirrored regions.
The command declares a region mirror set. Before any allocation takes place, all memory regions have their
internal "used size" property set to zero. Then, every time a memory region is populated by some content,
not only the populated memory region’s "used size" is expanded, but all mirrored regions' from the same
set.

The OVERLAY command can be useful on systems with limited resources. Suppose a microcontroller with
512 KB Flash and 32 KB RAM. And a program, with three algorithms, each of them 20 KB. If the user would
want all of these algorithms in RAM, without OVERLAY it would need 60KB of RAM.
RAM
+-------------------+
| Algorithm A 20 KB |
| Algorithm B 20 KB |
| Algorithm C 20 KB |
+-------------------+
This is impossible on a device with 32 KB RAM.

OVERLAY 0x20000000 : AT(...)
{
    .algoA { *(.algoA) }
    .algoB { *(.algoB) }
    .algoC { *(.algoC) }
}

.algoB VMA = 0x20000000
.algoC VMA = 0x20000000
But they will have different load address in Flash.
When needed the code in RAM can be manually replaced with the correct algorithms code during runtime.

clang supports embedding inline assembly in C/C++-code and follows the GNU syntax.
8.1. Syntax
__asm [volatile] (

    : <output operands>

Assembly string
An assembly string is a literal string containing assembler instructions and optional template strings.
A template string has the following syntax:
"%<modifier><number>"
"%<modifier>[<name>]"
The % token initiates the template string, followed by the optional <modifier> string that changes the way
the operand is printed in the final assembly string (see Assembly template string).
If numbered template strings are used, <number> refers to the operand at position number - 1 . The

Chapter 10. Attributes
The __attribute__ keyword allows to specify special attributes of variables, structure fields, functions, and
types.
The keyword format is either of the following:
__attribute__((attribute1, attribute2, ...))
__attribute__((__attribute1__, __attribute2__, ...))
For example:
int my_function(int b) __attribute__((const));
static int my_variable __attribute__((__unused__));
10.1. Function attributes
You can set function attributes in the declaration, the definition, or both. For example:
void AddGlobals(void) __attribute__((always_inline));
__attribute__((always_inline)) void AddGlobals(void) {...}
When function attributes conflict, the compiler uses the safer or stronger one. For example,
__attribute__((used)) is safer than __attribute__((unused)), and __attribute__((noinline)) is
safer than __attribute__((always_inline)).
If there exists no safe default, for example if two different calling conventions are specified, the compiler
emits an error.
For a list of available attributes in clang and their semantics, please refer to the Clang 21.1.0 attribute
reference.
10.1.1. __attribute__((section("name"))) function attribute
The section function attribute enables you to place code in different sections of the image.
EXAMPLE:

.text.

2 int foo(void)
3 {
4   return 2;
5 }
Section names must be unique. You must not use the same section name for different section types. If you
use the same section name for different section types, then the compiler merges the sections into one and

10.1.2. __attribute__((always_inline)) function attribute
Inlining heuristics are disabled and inlining is always attempted regardless of optimization level.
In some circumstances, the compiler might choose to ignore __attribute__((always_inline)), and not
inline the function. For example:
• A recursive function is never inlined into itself.
• Functions that use alloca() might not be inlined.
• A function is too large to be inlined efficiently or when the inlining would lead to code bloat or other
performance issues.
So while the always_inline attribute can be a strong suggestion to the compiler that a function
should be inlined, it does not provide a guarantee that the function will always be inlined in all
situations.
EXAMPLE:
int max(int x, int y) __attribute__((always_inline));
int max(int x, int y)
{
    return x > y ? x : y; // always inline if possible
}
RESTRICTIONS:
• This attribute is incompatible with the optnone attribute. Their simultaneous use throws the following
warning:

                                                   ^
                   note: conflicting attribute is here
• always_inline can be overridden by noinline attribute when used simultaneously.
Code 25. Function foo() will not be inlined

• Applying this attribute to a coroutine at the -O0 optimization level has no effect; other optimization levels
may only partially inline and result in a diagnostic.

10.1.4. __attribute__((gnu_inline)) function attribute
The gnu_inline changes the meaning of extern inline to use GNU inline semantics, meaning:
• If any declaration that is declared inline is not declared extern, then the inline keyword is just a hint. In
particular, an out-of-line definition is still emitted for a function with external linkage, even if all call sites
are inlined, unlike in C99 and C++ inline semantics.
• If all declarations that are declared inline are also declared extern, then the function body is present only
for inlining and no out-of-line version is emitted.
Some important consequences: static inline emits an out-of-line version if needed, a plain inline
definition emits an out-of-line version always, and an extern inline definition (in a header) followed by a
(non-extern) inline declaration in a source file emits an out-of-line version of the function in that source file
but provides the function body for inlining to all includers of the header.
RESTRICTIONS:
Either __GNUC_GNU_INLINE__ (GNU inline semantics) or __GNUC_STDC_INLINE__ (C99 semantics) will be
defined (they are mutually exclusive). If __GNUC_STDC_INLINE__ is defined, then the gnu_inline function
attribute can be used to get GNU inline semantics on a per function basis. If __GNUC_GNU_INLINE__ is
defined, then the translation unit is already being compiled with GNU inline semantics as the implied default.
It is unspecified which macro is defined in a C++ compilation.
GNU inline semantics are the default behavior with -std=gnu89, -std=c89, -std=c94, or -fgnu89-inline
compiler flags.

• data

Chapter 12. Inline functions
Inline functions provide a compromise between code size and performance. The decision whether to inline
the function is by default done by the compiler.
The compiler by default optimizes the code for performance concerning time. This makes execution faster by
eliminating the function-call overhead; in addition, if any of the actual argument values are constant, their
known values may permit simplifications at compile time so that not all of the inline function’s code needs to
be included. The effect on code size is less predictable; object code may be larger or smaller with function
inlining, depending on the particular case.
In the case the compilation restricts the code size, using the -Oz or -Os, the compiler tries to make sensible
inlining decisions and tries to keep the minimal code size.
12.1. Inline function declaration
There are different ways to declare an inline function, including:
inline
This keyword suggests to the compiler that it should consider inlining the function, but it’s not a
guarantee. The compiler will make the final decision based on the optimization level and other factors.
static inline
This keyword suggests that the function should be inlined in each translation unit that uses it. This
keyword implies that the function is only visible within its translation unit, so it cannot be used by other
translation units. See also the __attribute__((gnu_inline)) function attribute chapter for more details.
always_inline
This attribute suggests that the function should always be inlined, regardless of the optimization level.
However, it does not guarantee that the function will always be inlined. Furthermore, it can also be
overridden by other compiler flags or settings that disable inlining. See also the
__attribute__((always_inline)) function attribute chapter for more details.
extern inline
This keyword suggests that the function is inline but defined in another translation unit. This keyword
allows the function to be used by other translation units. See also the __attribute__((gnu_inline))
function attribute chapter for more details.
noinline
This attribute suggests that the function should not be inlined, regardless of the optimization level. This
keyword can be used to prevent inlining of functions that have side effects or are too large to be inlined
efficiently. See also the __attribute__((noinline)) function attribute chapter for more details.
For further information, please refer to the Function attributes chapter or Clang 21.1.0 attribute reference.
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   92

12.2. Inlining constraints
There are certain constrains in a function definition that can make it unsuitable for inline substitution. These
are common situations when a function may fail to inline:
• No optimization level was used for the compilation unit ( -O0`) and the function wasn’t declared with
__attribute__((always_inline)) or [[gnu::always_inline]] (C++-only) or
[[clang::always_inline]] (C++-only)
• no optimization level was used for the compilation unit ( -O0) and the function call wasn’t marked with
[[clang::always_inline]] (C++-only)
• The function was declared with __attribute__((optnone)) function attribute.
• The function is non-trivial and recursive or calls alloca function.
• The function is defined outside the caller’s compilation unit and link-time optimization isn’t enabled.
• There is no definition available for the called function or method. In this case, there is no opportunity to
inline.
• The LocationContext chain for a given ExplodedNode reaches a maximum cutoff depth. This prevents
unbounded analysis due to infinite recursion, but also serves as a useful cutoff for performance reasons.
• The function is variadic (one which accepts a variable number of arguments). This is not a hard limitation,
but an engineering limitation.
12.3. Linking restrictions
For a function with external linkage, the following restrictions apply:
• If a function is declared with an inline function specifier, then it has to also be defined in the same
translation unit.
• If all of the file scope declarations for a function in a translation unit include the inline function specifier
without extern, then the definition in that translation unit is an inline definition.
• An inline definition does not provide an external definition for the function, and does not forbid an
external definition in another translation unit.
• An inline definition provides an alternative to an external definition, which a translator may use to
implement any call to the function in the same translation unit. It is unspecified whether a call to the
function uses the inline definition or the external definition.
12.3.1. Resolving undefined symbol linker error
• If the function is defined outside the caller’s compilation unit and inlining is desired, the function’s
definition should be marked with the inline keyword and moved to a header file included in all files that
want to call it. Now, if it fails to inline, the linker will emit an error.
ld.lld: error: undefined symbol ...
If it is desired for the function to instead fail to inline, in a single compilation unit, an extern inline

function declaration should be placed.

12.4. C99 inline functions
By default, clang builds C code in GNU C17 mode, so it uses standard C99 semantics for the inline
keyword. These semantics are different from those in GNU C89 mode, which is the default mode in versions
of GCC prior to 5.0. For example, consider the following code:
inline int add(int i, int j) { return i + j; }
int main() {
  int i = add(4, 5);
  return i;
}
In C99, inline means that a function’s definition is provided only for inlining, and that there is another
definition (without inline) somewhere else in the program. That means that this program is incomplete,
because if add isn’t inlined (for example, when compiling without optimization), then main will have an
unresolved reference to that other definition. Therefore we’ll get a (correct) link-time error like this:
Undefined symbols:
  "_add", referenced from:
      _main in cc-y1jXIr.o
By contrast, GNU C89 mode (used by default in older versions of GCC) is the C89 standard plus a lot of
extensions. C89 doesn’t have an inline keyword, but GCC recognizes it as an extension and just treats it as a
hint to the optimizer.
There are several ways to fix this problem:
• Change add to a static inline function. This is usually the right solution if only one translation unit needs to
use the function. static inline functions are always resolved within the translation unit, so you won’t have
to add a non-inline definition of the function elsewhere in your program.
• Remove the inline keyword from this definition of add. The inline keyword is not required for a function
to be inlined, nor does it guarantee that it will be. Some compilers ignore it completely. clang treats it as a
mild suggestion from the programmer.
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   94
--- PAGE 101 ---
• Provide an external (non-inline) definition of add somewhere else in your program. The two definitions
must be equivalent!
• Compile in the GNU C89 dialect by adding -std=gnu89 to the set of clang options. This option is only
recommended if the program source cannot be changed or if the program also relies on additional C89-
specific behavior that cannot be changed.
All of this only applies to C code; the meaning of inline in C++ is very different from its meaning in either
GNU89 or C99.
For more information, please refer to the Language Compatibility C compatibility C99 inline functions.

12.6. Conclusion
In general, it’s best to use the inline keyword and let the compiler decide whether to inline the function or

SHF_WRITE

SHF_ALLOC
The section occupies memory during process execution. Some control sections do not reside in the

SHF_EXECINSTR

SHF_MERGE
The data in the section may be merged to eliminate duplication. Unless the SHF_STRINGS flag is also
set, the data elements in the section are of a uniform size. The size of each element is specified in the
section header’s sh_entsize field. If the SHF_STRINGS flag is also set, the data elements consist of
null-terminated character strings. The size of each character is specified in the section header’s

SHF_STRINGS

incorrect behavior. If this section has either an sh_type value or contains sh_flags bits in the OS-

values, then the link editor should reject the object file containing this section with an error.

SHF_TLS
This section holds Thread-Local Storage, meaning that each separate execution flow has its own
distinct instance of this data. Implementations need not support this flag.
SHF_COMPRESSED

E.1. Linker Script
SUBCLAUSE
Symbol assignment
REFERENCE
https://lld.llvm.org/ELF/linker_script.html
BEHAVIOR
A symbol assignment looks like:
symbol = expression;
symbol += expression;
The first form defines symbol. If symbol is already defined, it will be overridden. The other form requires
symbol to be already defined.
For a simple assignment like alias = aliasee;, the st_type field is copied from the original symbol. Any
arithmetic operation (e.g. + 0 will reset st_type to STT_NOTYPE.
The st_size field is set to 0.
SUBCLAUSE
SECTIONS command
REFERENCE
https://lld.llvm.org/ELF/linker_script.html
BEHAVIOR
A SECTIONS command looks like:
SECTIONS {
  section-command
  section-command
  ...
} [INSERT [AFTER|BEFORE] anchor_section;]
Each section-command can be a symbol assignment, an output section description, or an overlay
description.
When the INSERT keyword is present, the SECTIONS command describes some output sections which
should be inserted after or before the specified anchor section. The insertion occurs after input sections have
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   106
--- PAGE 113 ---
been mapped to output sections but before orphan sections have been processed.
In the case where no linker script has been provided or every SECTIONS command is followed by INSERT,
LLD applies built-in rules which are similar to GNU ld’s internal linker scripts.
• Align the first section in a PT_LOAD segment according to -z noseparate-code, -z separate-code, or
-z separate-loadable-segments
• Define __bss_start, end, _end, etext, _etext, edata, _edata
• Sort .ctors.*/.dtors.*/.init_array.*/.fini_array.* and PowerPC64 specific .toc
• Place input .text.* into output .text, and handle certain variants ( .text.hot., .text.unknown.,
.text.unlikely., etc) in the presence of -z keep-text-section-prefix.
SUBCLAUSE
Output section description
REFERENCE
https://lld.llvm.org/ELF/linker_script.html
BEHAVIOR
The description of an output section looks like:
section [address] [(type)] : [AT(lma)] [ALIGN(section_align)]
[SUBALIGN(subsection_align)] {
  output-section-command
  ...
} [>region] [AT>lma_region] [:phdr ...] [=fillexp] [,]
Output section address
When an OutputSection S has address, LLD will set sh_addr to address.
The ELF specification says: "The value of sh_addr must be congruent to 0, modulo the value of
sh_addralign."
The presence of address can cause the condition unsatisfied. LLD will warn. GNU ld from Binutils 2.35
onwards will reduce sh_addralign so that sh_addr=0 (modulo sh_addralign).
When an output section has no input section, GNU ld will eliminate it if it only contains symbol assignments
(e.g. .foo { symbol = 42; } ). LLD will retain such sections unless all the symbol assignments are
unreferenced PROVIDED.
When an output section has no input section but advances the location counter, GNU ld sets the SHF_WRITE
flag. LLD sets the SHF_WRITE flag only if the preceding output section with non-empty input sections also
has the SHF_WRITE flag.
Output section type
When an OutputSection S has (type), LLD will set sh_type or sh_flags of S. type is one of:
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   107
--- PAGE 114 ---
• NOLOAD: set sh_type to SHT_NOBITS.
• COPY, INFO, OVERLAY: clear the SHF_ALLOC bit in sh_flags.
• TYPE=<value>: set sh_type to the specified value. <value> must be an integer or one of SHT_PROGBITS,
SHT_NOTE, SHT_NOBITS, SHT_INIT_ARRAY, SHT_FINI_ARRAY, SHT_PREINIT_ARRAY.
When sh_type is specified, it is an error if an input section in S has a different type.
Output section alignment
sh_addralign of an OutputSection S  is the maximum of ALIGN(section_align) and the maximum
alignment of the input sections in S.
When an OutputSection S has both address and ALIGN(section_align), GNU ld will set sh_addralign
to ALIGN(section_align).
Output section LMA
A load address (LMA) can be specified by AT(lma) or AT>lma_region.
• AT(lma) specifies the exact load address. If the linker script does not have a PHDRS command, then a
new loadable segment will be generated.
• AT>lma_region specifies the LMA region. The lack of AT>lma_region means the default region is used.
Note, GNU ld propagates the previous LMA memory region when address is not specified. The LMA is
set to the current location of the memory region aligned to the section alignment. If the linker script does
not have a PHDRS command, then if lma_region is different from the lma_region for the previous
OutputSection a new loadable segment will be generated.
The two keywords cannot be specified at the same time.
If neither AT(lma) nor AT>lma_region is specified:
• If the previous section is also in the default LMA region, and the two section have the same memory
regions, the difference between the LMA and the VMA is computed to be the same as the previous
difference.
• Otherwise, the LMA is set to the VMA.

F.2. The startup code
Initializing an embedded system usually requires a combination of hardware, run-time, library and
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   111
--- PAGE 118 ---
application setup. You may want to perform all of these in your own code, or you be able to use the Picolibc
startup code. Either works fine, using the Picolibc code means writing less of your own.
F.2.1. Picocrt — Picolibc startup code
Picocrt is the crt0.o code provided by Picolibc. It goes through a sequence of initialization steps, many of
which you can plug your own code into:
1. Architecture-specific runtime initialization. For instance, RISC-V needs the gp register initialized for quick
access to global variables while ARM with hardware floating point needs to have the FPSCR register set
up to match C semantics for rounding.
2. Data initialization. Here is the code inside Picocrt:
memcpy(__data_start, __data_source, (uintptr_t) __data_size);
For this to work, the linker script must assign correct values to each of these symbols:
• __data_start points to the RAM location where the .data segment starts.
• __data_source points to the Flash location where the .data segment initialization values are stored.
• __data_size is an absolute symbol noting the size of the initialized data segment.
3. BSS initialization. Here is the code inside Picocrt:
memset(__bss_start, '\0', (uintptr_t) __bss_size);
Assign these symbols in the linker script as follows:
• __bss_start points to the RAM location where the .bss segment starts.
• __bss_size is an absolute symbol noting the size of the cleared data segment.
4. Optionally call constructors:
• The default and the hosted crt0 variants call initializers/constructors using __libc_init_array().
• The minimal crt0 variant doesn’t call any constructors.
5. Call main().
6. After main() returns:
• The default and the minimal crt0 variants run an infinite loop if main() returns.
• The hosted crt0 variant calls exit, passing it the value returned from main().
F.2.2. crt0 variants
The base crt0 version provided by Picolibc calls any constructors before it calls main() and then goes into
an infinite loop after main() returns to avoid requiring an _exit() function.
In an environment which provides a useful _exit() implementation, applications may want to use the
crt0-hosted variant that calls exit() when main() returns, resulting in a clean return to the hosting
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   112

F.2.3. Semihosting
Semihosting is a mechanism used when the application is run under a debugger or emulation environment
that provides access to some functionality of the OS running the debugger or emulator. Picolibc has
semihosting support for console I/O and the exit() call.
One common use for semihosting is to generate debug messages before any of the target hardware has
been set up.
Picolibc distributes the semihosting implementation as a separate library, libsemihost.a. This library also
resides inside the riscv/lib directory, next to the libc.a variant corresponding to the selected
configuration.

F.3. Linking Picolibc applications
Linking embedded applications requires significant target-specific information, including the location of
various memory sections along with a range of application-specific memory settings.
You can create your own custom linker script , or you can use the linker script provided by Picolibc . This
section describes how to do either.
F.3.1. Creating a custom linker script
Aside from the application and hardware specific aspects of creating a linker script, if your application is
using the Picolib startup code, then you need to define the addresses used in that code, and set up the data
as required. Check out the Initializers in Picolibc section for details on what names to declare. You will need
to use the compiler option -T.
F.3.2. Using picolibc.ld
Picolibc provides a default linker script which can often be used to link applications, providing that your
linking requirements are fairly straightforward. To customize picolibc.ld, you will create a custom linker
script that sets up some variables and then INCLUDEs picolibc.ld. Here is a sample custom linker script
sample.ld:
Code 31. sample.ld
__flash = 0x80000000;
__flash_size = 0x00080000;
__ram = 0x80080000;
__ram_size = 0x40000;
__stack_size = 1k;
INCLUDE picolibc.ld
This is a configuration that is compatible with qemu and nsim.
To use this with clang, the command line would look like this:
clang ... -Tsample.ld
The resulting executable file can be run with nsim with the help of the following command:
nsimdrv ./program.elf -prop=nsim_isa_family=rv32 -prop=nsim_isa_ext=-all.i.a.m.zicsr.zbb
-prop=icnts=1 -prop=nsim_print_stats_on_exit=1 -prop=enable_exceptions=off
-prop=nsim_semihosting=1
Alternatively, you can specify those values using --defsym and use picolibc.ld as the linker script:
clang -Wl,--defsym=__flash=0x80000000 -Wl,--defsym=__flash_size=0x00400000 -Wl,
--defsym=__ram=0x80400000 -Wl,--defsym=__ram_size=0x00200000 ... -Tpicolibc.ld
The picolibc.ld script sets defaults for these values in case they are not defined (so picolibc.ld is
usable by itself without specifying any --defsym), which might or might not be suitable for your targeted

F.3.3. Defining Memory Regions
picolibc.ld defines only two memory regions: flash and ram.
flash
Addressable region of read-only memory which holds program text, constant data and initializers for
read-write data.
ram
Read-write memory which needs to be initialized before your application starts.
As shown at Using picolibc.ld, you declare the base and size of both memory regions in your linker script:
• __flash specifies the lowest address in read-only memory used by your application. This needs to be in
flash, but need not be the start of actual flash in the device.
• __flash_size specifies the amount of read-only memory you want to allow the application to fill. This
need not be all of the available memory.
• __ram specifies the lowest address you want the linker to allocate to read-write data for the application.
• __ram_size specifies the maximum amount of read-write memory you want to permit the application to
use.
• __stack_size reserves this much space at the top of ram for the initial stack.
• __heap_size_min is an optional value that you can set to ensure there is at least this much memory
available for the heap used by malloc().
malloc() will still be able to use all memory between the end of pre-allocated data and the bottom of the
stack area.

F.4. Thread Local Storage in Picolibc
The standard C library API includes many functions that use persistent state held by the library not the
application. One obvious example is errno, a global variable originally designed to hold error status from the
Unix kernel, but which was co-opted by libc to provide additional error status values from the library itself.
There are numerous other examples of this kind of state.
To permit multiple threads sharing a single address space to use the library without conflicting over this
data, each thread needs a private copy of data that it uses. Newlib did this by creating a global structure
holding all thread-specific values and then defining an API for the library to get the global structure for the
current thread.
Picolibc does this by using the built-in thread-local-storage mechanisms in the toolchain. This has several
benefits:
1. Source code is simpler as thread-local variables are accessed directly by name.
2. Thread local storage contains only values used by the application.
3. Generated code is smaller and faster.
F.4.1. TLS model used by Picolibc
Picolibc is compiled with -ftls-model=local-exec. Applications should include -ftls-model=local
-exec in their compile commands.
local-exec defines a single block of storage for all TLS variables. Each TLS variable is assigned an offset
within this block and those values are placed in the binary during relocation.

be initialized as a part of the normal data/bss initialization process for the application.

3. Clear __tbss_size bytes starting __tdata_size bytes into the new block
4. Set the TLS pointer as necessary

clearing values in the uninitialized data portion.
Picolib also provides architecture-specific internal APIs as necessary, for example, __aeabi_read_tp for
ARM processors.

F.5. Initializers / Constructors and Finalizers / Destructors
The __libc_init_array() and __libc_fini_array() functions in Picolibc are called by Picocrt during
application startup and shutdown. If you have custom start up code that replaces Picocrt, you probably want
to call these as well.
__libc_init_array()
This function performs application initialization by calling:
1. Functions listed in the preinit array
2. _init() function
3. Functions listed in the init array
_init()
Your program may declare an optional initialization function called _init(). If such a function is
included in the binary it will be called before the init array contents are evaluated.
__libc_fini_array()
Most embedded applications never return from main(), but if yours does, Picocrt will call:
1. Functions listed in the fini array
2. _fini() function
_fini()
Your program may declare an optional finalization function called _fini(). If such a function is
included in the binary it will be called after the fini array contents are evaluated.
F.5.1. Automatically generated arrays of function pointers
The .preinit_array, .init_array and .fini_array segments are built by the linker using data
generated by the compiler. When you decorate a function with __attribute__((constructor)), the compiler
places the address of the function into the .init_array segment. Decorate a function with
__attribute__((destructor)) and the compiler will place its address in the .fini_array segment. The
.preinit_array segment is generated internally by the compiler for things like C++ vtable validation.
The linker script should collect all of the data from these segments into memory (probably flash as it doesn’t
change) so that the image ends up with arrays of function pointers. For data from the .init_array
segment, the array should start with the symbol __init_array_start and ending with
__init_array_end. For data from the .fini_array segment, the array should start with the symbol
__fini_array_start and end with __fini_array_end. Finally, for data from the .preinit_array
segment, the array starts with __preinit_array_start and ends with __preinit_array_end.
Each of these arrays are complicated by the optional priority assigned to destructors and constructors, and
the presence of the deprecated .ctors and .dtors segments.

F.6. System Interfaces used by Picolibc
F.6.1. stdin, stdout and stderr
Picolibc stdio splits support for simple console input/output and more complex file operations so that a
minimal system can easily support the former with only a few functions.
To get stdin / stdout / stderr working, the application needs to define the stdin, stdout and stderr
globals, which contain pointers to FILE objects. The pointers may reside in read-only memory, but the FILE
objects may not. A single FILE object may be used for all three pointers, and linker aliases may be used to
make all three pointers be stored in the same location. The FILE object contains function pointers for
putc(), getc(), which might be defined as follows:
static int sample_putc(char c, FILE *file) {
  (void) file;        /* Not used in this function */
  __uart_putc(c);     /* Defined by underlying system */
  return c;
}
static int sample_getc(FILE *file) {
  (void) file;        /* Not used in this function */
  unsigned char c = __uart_getc();  /* Defined by underlying system */
  return c;
}
It also contains a pointer to an optional flush() function, which, if provided, will be called to flush pending
output to the file, e.g., when the fflush() function is called:
static int sample_flush(FILE *file) {
  /* This function doesn't need to do anything */
  (void) file;        /* Not used in this function */
  return 0;
}
These functions are used to initialize a FILE structure:
static FILE __stdio = FDEV_SETUP_STREAM(sample_putc, sample_getc, NULL, _FDEV_SETUP_RW);
This defines a FILE which can read and write characters using the putc() and getc() functions described
above, but not using any flush() function. The final parameter, which specifies the operations supported,
can be one of the following:
Mode Operations Required Functions
_FDEV_SETUP_READ Read getc()
_FDEV_SETUP_WRITE Write putc()
_FDEV_SETUP_RW Read/Write putc(), getc()
Finally, the FILE is used to initialize the stdin, stdout and stderr values, the latter two of which are simply
aliases to stdin:
Copyright © 2026 HighTec EDV-Systeme GmbH RISC-V Development Platform - User Guide   |   122
--- PAGE 129 ---
FILE *const stdin = &__stdio;
__strong_reference(stdin, stdout);
__strong_reference(stdin, stderr);
The semihosting library libsemihost.a contains default implementations for all of the above, so by linking
it, stdin, stdout and stderr will be available.
F.6.2. fopen(), fdopen()
Support for these requires malloc() / free() along with a handful of POSIX-compatible functions:
int open (const char *, int, ...);
int close (int fd);
ssize_t read (int fd, void *buf, size_t nbyte);
ssize_t write (int fd, const void *buf, size_t nbyte);
off_t lseek (int fd, off_t offset, int whence);
The code needed for this is built into Picolibc.
F.6.3. exit()
exit() is just a wrapper around _exit() that also calls destructors and callbacks registered with
atexit(). To make it work, you will need to implement the _exit() function:
void _exit (int status) __attribute__((__noreturn__));
F.6.4. sbrk()
Picolibc includes a simple version of sbrk that can return chunks of memory from a pre-defined contiguous
heap. To use this function, your application linking process needs to define two symbols:
• __heap_start - points at the start of the heap available for sbrk().
• __heap_end - points at the end of the heap available for sbrk().
The sample linker script provided with Picolibc defines these two symbols to enclose all RAM which is not
otherwise used by the application.

Appendix G: Known limitations
• Missing support for C++ threads.
• The help screen shown by the tools might list options supporting other targets that are unrelated to the
RISC-V support and can be ignored.
• The following C / POSIX library functions are not supported: at_quick_exit, quick_exit, sigprocmask,
open64, stat, access, alarm, chdir, chmod, dup, dup2, link, rmdir, sleep, truncate, wait, waitid and
waitpid.
• The strtold/wcstold functions are not supported and math functions operating on long double typed
operands might not set the FE (floating-point environment) exception flags.
• The C++ libraries are shipped with stdin support disabled. Related symbols like std::cin will not be
available. Should you need a version with stdin support enabled, contact support@hightec-rt.com.
• The user guide is not complete and it may contain obsolete or unrelated information.
• Temporary no multilib is supplied for targets that use vector extensions.
• printf output is not flushed at program exit if the printed string is not terminated with a newline
character (\n).
